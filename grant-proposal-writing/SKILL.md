# 中文课题申报书写作

## 用途

帮助撰写、重构、润色中文课题申报书。这类文档有稳定的评审预期：结构规范、语言学术化且务实、重心突出、篇幅受控。本 skill 把一次完整重构中踩过的坑固化为可复用的规范与工具，避免重复犯错。

> **配套 skill 与文件位置**：本 skill 只保留申报书**特有的结构规范**——`references/结构与篇幅.md`（主线重心、章节骨架、页数分配、拟题）。**通用写作工序（去AI味、去列表化、学术化过稿、docx 出稿、审阅）已抽到配套 skill `chinese-formal-writing`**。下文凡以 `chinese-formal-writing/` 开头的路径均指该 skill 的 references/scripts，不在本目录（`结构与篇幅.md` 例外，是本 skill 自带的）。建议两个 skill 一起安装；未装配套 skill 时，本文的要点提示仍可用，只是缺少那几份详细清单与出稿脚本。

**核心教训（每次都要盯住的四类问题）：**
1. **AI味与口语味** —— 英文缩略语堆砌、括号补丁/免责反复、表格矩阵过密、口号式三字/四字并列、双引号和破折号泛滥；以及最隐蔽、最常被评审点名的口语化衔接词（"需要说明的是""总体而言""在此基础上"）、工作汇报腔（"陆续上线""稳步推进""扎实落地"）、段落首句非主题句、形容词与程度副词滥用（"显著""实质性推进""核心突破"）、标题口号化或夹带管理黑话（"赋能""抓手""闭环""底座"）。
2. **像列表不像论述** —— "目标:/主要内容:(1)(2)"式条目、加粗编号小标题、表格，读起来机械。
3. **重心失衡** —— 本该是主线的内容被次要方面（技术保障、风险防控、合规、平台建设这类素材多、容易写长的部分）淹没。
4. **篇幅膨胀** —— 免责与边界说明各段重复、同一概念多处逐字复述、AI润色时越改越长。

## 文风定位：学术方案体

申报书介于学术论文与项目报告之间，语言容易在"学术论证"和"工作汇报"之间摇摆——这是上述口语味、汇报腔的深层根源。理想的定位是**以学术语言承载落地思考**：问题的提出是学术的，解决路径是务实的；概念定义严谨，方法描述可操作。全篇大体上前半（背景、进展、目标、内容）偏学术论证、核心是"说清为什么"，后半（进度、组织、经费、风险）偏方案陈述、核心是"说清怎么做"；平衡点在于**不因学术化而空洞，不因方案化而随意**。它既不是论文的模仿，也不是报告的复制。

## 何时用本 skill

- 从零写一份申报书，或按评审/导师意见重构现稿；
- 用户抱怨"AI味太重""太像列表""页数太多""某部分写太多，喧宾夺主"；
- 需要把 Markdown 大纲转成符合中文公文格式的 docx；
- 需要逐段或分批审阅打磨已有稿件。

**何时不用/谨慎用**：英文 proposal、论文投稿稿、商业标书不直接套用本 skill 的中文公文规范；伦理申请、经费预算等强表单文本以及**固定表格模板**的申报书，优先按模板逐栏填写，不要强行改成连续段落的报告体。这些情形可借鉴去口语化、术语一致等通用条目，但结构与格式规则不照搬。

## 动手前必须问清楚（最重要）

**不要一上来就写。** 主线、章节结构和导出格式如果没对齐，写完再返工代价极大。开始前先问清三件事，把答案写进计划文件：

1. **主线是什么？** 这份申报书的核心要讲的那件事是什么、哪几项内容是主线、哪些是配角（保障/支撑）。**这是全篇重心排布的依据**，必须先和用户确认，不能自己猜。问法举例："这个课题的主线我理解是〔某某研究要解决的核心问题/要提出的核心方法〕，而〔技术保障、风险防控、平台建设等〕只是配套——对吗？主线具体是哪几块？" 主线确定后，研究内容条目和报告章节都要让主线独立成条/成章并前置，配角整合收敛（见 `references/结构与篇幅.md`）。
2. **章节组织有没有固定要求？** 很多基金/主管单位对申报书的栏目、章节、提纲有硬性规定（如固定的一级栏目、必填小节、字数或页数分配）。先问清有没有这类要求。**如果用户提供了规定的章节组织，务必原样落盘持久化**——写进计划文件，或单独存一个 `章节要求.md`（逐字保留栏目名与顺序，不要自行增删改名）。此后**一切结构安排以此为准，不套用通用骨架**；主线的重心排布也要在这个固定框架内实现（例如让核心内容占更靠前、更充实的规定栏目）。若没有固定要求，才用 `references/结构与篇幅.md` 的通用骨架自拟。
3. **导出 docx 的格式要求是什么？** 一开始就问清楚，不要等出稿时才发现字体字号不对。逐项确认：一级/二级/三级标题各用什么字体字号、是否加粗；正文字体字号；行距（固定值多少磅还是倍数）；对齐方式；首行缩进；页边距/页码等。有申报通知/模板的，让用户直接给通知原文或模板文件。把确认到的格式参数记进计划文件，出稿脚本按它设置（默认值与设置方法见 `chinese-formal-writing/references/格式与docx.md`）。

其余需要在计划阶段一并确认的：课题标题改不改、篇幅上限（页数）、涉密/边界如何处理、有无必须统一的固定术语、经费与周期等数字是否已定（未定就不要写死）。

## 总体工作流

**动手前先完成上面三问，然后写"说明与分解计划"，不要直接动手改正文。** 计划这一步与用户对齐目标、诊断现稿、确定重构方案，避免大改后返工。

1. **建子文件夹 + 写计划文件**（如 `00-说明与分解计划.md`）。计划文件包含：**主线定位**（第 1 问的确认结果）、**章节结构**（第 2 问：有固定要求就逐字持久化那套栏目/提纲，没有就是自拟的骨架）、**导出格式参数**（第 3 问，逐项列出字体字号行距等）、本轮目标（逐条对应用户/评审意见）、对现稿的诊断（重心、AI味、冗余）、重构后的结构方案（研究内容条目、报告章节与页数预估）、写作规范、分步任务清单。**在计划里就地向用户确认关键决策**（主线怎么定、章节按不按固定要求、重心怎么搬、格式怎么要求、标题改不改、涉密怎么处理），确认后再逐节实施。
2. **逐节实施**，一节一个文件（如 `01-研究目的和意义.md` … `09-附件-主体报告提纲.md`）。每节写完可暂停复核。
3. **合稿**：把各节 `cat` 成一个总文件，加主标题，节间不留 `---` 分隔线。
4. **出 docx**：顺序为**先修引号 → pandoc 转 docx → python-docx 套格式**（引号必须在 pandoc 前修，否则 smart 会把中文引号全变右引号）。见 `chinese-formal-writing/references/格式与docx.md`。
5. **审阅**：多进程/逐段审阅，改完再审。见 `chinese-formal-writing/references/审阅prompt.md`。终稿前按 `chinese-formal-writing/references/学术化过稿清单.md` 分遍专项检查（每遍只查一类：口语词/三字并列/形容词/长句/术语一致/主题句），不要一次通读求全。

每完成一节或一轮大改，都应征求用户确认或让其复核，不要一口气改到底。若用户明确要求一次性完成、或当下无法逐节确认，则**先列出所做的关键假设**（主线、格式、页数、涉及的数据与未定数字）再推进，并在交付时把这些待确认项显著标出。

## 四类问题的处置要点

改稿时按下面四个方向排查，详细清单见 references：

- **去AI味与口语味**：见 `chinese-formal-writing/references/去AI味核对清单.md`（16 类）。要点：英文缩略语首次给中文全称、正文尽量用中文；双引号与破折号能省则省（双引号常能从上百对压到个位数）；不写"可评可管可推广"这类口号并列；删口语衔接词（"需要说明的是""在此基础上""与此同时"）与汇报腔（"陆续上线""稳步推进"）；程度副词（"显著""实质性推进""核心突破"）改客观陈述；长句定语超三个即拆；段落首句必须是概括本段的**主题句**。终稿前用 `chinese-formal-writing/references/学术化过稿清单.md` 分遍过一遍。
- **去列表化**：把"目标:/主要内容:(1)(2)"、加粗编号小标题、表格改写为连续段落，每段以主题句领起、用过渡句衔接。表格数量以信息密度与申报通知为准，只留能显著提高可读性的关键表，其余化为叙述或下沉附录。详见 `chinese-formal-writing/references/去列表化改写.md`。
- **重心与篇幅**：主线内容独立成章/成条并前置，次要方面（技术保障、风险、合规等）整合收敛为一章/一条，别铺开。主体报告提纲控制在约定页数内，细节沉到附录。边界与免责集中在"研究范围界定"处讲一次，后文不重复。详见 `references/结构与篇幅.md`。
- **提防膨胀**：AI 润色时倾向于加长、把删掉的列表/术语/表格重新加回、擅自新增数字或结论。每轮改完对比字数，盯住这几点。

## 敏感/涉密内容的边界约束（如课题涉及才用）

若课题涉及敏感、涉密或受限数据、场景或伦理审查（如政务、国防、医疗、人口等），正文宜有一段明确的研究边界说明，且全文一致，按申报通知、伦理规范与数据管理要求来定。常见可选表述：相关研究限于不接触真实敏感信息的部分（机制设计、合规映射、桌面推演等）；实验仅用合成/脱敏/公开数据，不接触真实敏感系统。**注意：原型是否部署、试点或移交，以课题任务书和主管要求为准**——工程、医学转化、平台建设类课题往往需要真实部署，不可一律写"不上线、不部署、不移交"。这段话集中讲一次即可，后文不重复；不涉及敏感内容的课题可跳过本节。

**AI 操作边界**：写作过程本身也要守这条线。若用户提供真实涉密材料、未脱敏数据或真实业务系统信息，先要求脱敏或改用合成样例，不要把真实敏感信息带入模型处理或写进稿件。

## 关键提醒

- **术语全文统一**。改稿前先把本课题的关键术语约定成固定提法（同一概念只用一个词、有全称的不随意简写、分类口径首次给全后不变），审阅时把术语一致性作为硬约束，防止 AI 各段用词漂移。模板见 `chinese-formal-writing/references/学术化过稿清单.md` 的术语表。
- **标题要专业**。研究内容/章节/创新点标题用规范学术名词短语，不用口号式动词并列（如"……赋能业务、提升……质量的方法"）、不用管理黑话（赋能、抓手、闭环、底座等），同级标题句式与粒度一致。拟题要点见 `结构与篇幅.md`。
- **有意保留的结构标记不要删**。关键问题/创新点里的"第一/第二…"序数、进度里的"第一阶段…"是便于评审数点和看时间轴的，逐段审阅时提醒 AI 不要当作列表清掉。
- **不要写死不确定的数字**（经费额度、周期月数等），除非用户已确认；也不要写"短周期""小型""报告型"这类自我贬低的限定。
- **docx 格式**：以申报通知/模板为准；无明确要求时用常见默认——一级标题黑体三号加粗、二三级标题楷体_GB2312 三号、正文仿宋_GB2312 三号（行距 28 磅 EXACTLY、两端对齐、首行缩进 2 字、黑色）。脚本参数按实际要求改。pandoc smart 会把中文引号全转成右引号，必须用状态机把成对引号修回来。脚本见 `chinese-formal-writing/scripts/`。
