# 标注约定

`SECTIONS` 的写法、条目字段的取值、以及 `why` 的写作规范。

---

## SECTIONS 的组织

一个 `<section>` 对应稿件里的一个自然单元（一个小节、一段、一张图、或一组跨章节的同类问题）。

```html
<section>
  <div class="sec-head">
    <h2>3.1 &nbsp;Motivating Observation</h2>
    <span class="loc">main.tex:328-336</span>
    <span class="sec-note">全段</span>
  </div>
  <p class="prose">
正文，内联标记写在这里。
  </p>
</section>
```

- `h2` 用稿件里的原始编号与标题，作者能直接对上
- `.loc` 精确到行号区间
- `.sec-note` 写这一节是「全段」「节选（仅含改动句）」「建议合并」之类的元信息

**长段落只标改动句**，其余用 `<span class="snip">〔……〕</span>` 略过。贴全文反而淹没改动。`.snip` 也用来标注上下文来源：`<span class="snip">〔Settings 段，:331〕</span>`。

**跨章节的同类问题可以单独成节**，例如「与其他章节的记号衔接」「复现所需但未报告的事实」——这类问题没有单一归属位置，集中放比硬塞进某一段好。

## 四类标记

```html
<!-- 修改 -->
<span class="chg" data-id="a1"><del>旧文本</del><ins>新文本</ins></span>

<!-- 新增 -->
<span class="chg" data-id="a2"><ins>补写的内容</ins></span>

<!-- 删除 -->
<span class="chg" data-id="a3"><del>建议删掉的内容</del></span>

<!-- 结构（独占一行的段落级标记） -->
<span class="chg brk" data-id="a4" data-type="结构"><ins>¶ 建议此处另起一段</ins></span>
```

配色沿用校对符号传统：**蓝墨水＝新增、红笔＝删除、赭石＝改写、紫＝结构**。

`data-type` 只在结构类需要手写；其余由条目的 `type` 字段自动决定样式。

### 一个 id 用在多处

同一处改动横跨几个位置时（同一个词要在三处统一、同一句话拆成几段修），用同一个 `data-id`。点击任意一个会全部高亮，编号也相同。条目的 `loc` 写成 `main.tex:143（2 处）`。

### 编号是自动的

页面加载时按 DOM 顺序给每个唯一 id 分配上标编号，不需要手写。所以插入新条目时**不用重排编号**。

## 条目字段

```python
'a1': dict(
    src='both',            # mine | codex | both
    sev='必改',            # 必改 | 建议 | 润色
    type='修改',           # 修改 | 新增 | 删除 | 结构
    cat='悬垂修饰',        # 短标签，出现在弹窗的分类 chip 上
    loc='main.tex:143',    # 精确位置，跨位置写「（3 处）」或「（对照 :288）」
    before='原文……',       # 纯新增时写「（原文无此内容）」+ 上下文
    after='改后……',        # 可以是具体文本，也可以是操作说明
    why='……',              # 支持行内 HTML
),
```

### `cat` 的写法

短、具体、可分类。好的：`引用错论文`、`符号冲突`、`二次舍入`、`选择性报告`、`浮动体错位`、`与算法不符`。差的：`表述问题`、`需要改进`。

### `sev` 的判据

判据是**会不会被当场发现，以及发现后的代价**，不是改起来费不费力。

- **必改** —— 一眼可见、或可当场核查坐实：占位符残留、编译进 PDF 的编辑标记、前后矛盾的数字、引用错论文、页数超限、语法错误
- **建议** —— 影响说服力与评分但不是错：论证缺口、overclaim、缺限定、结构问题
- **润色** —— 只影响观感：术语统一、冗词、排版细节

**必改项应当少而硬。** 作者赶时间时第一件事是筛「仅必改」，那份清单必须真的是「不改就完了」的东西。一章 30 处里 25 处必改，说明分档失效了。

### `before` / `after`

- `before` 引**原文**，不要转述。长句可以截断但要保留出问题的部分。
- 纯新增时 `before` 写 `（原文无此内容）` 并补一句上下文说明它插在哪。
- `after` 可以是可直接替换的文本，也可以是操作说明（`将整个 figure* 环境移到 :714 之后`）。**涉及数值但需要作者填的，用 `$\langle\text{填实际值}\rangle$` 占位，不要编数字。**

---

## `why` 的写作规范

**这是整个 skill 的价值所在。** `before`/`after` 只是 diff，任何工具都能给。

一条合格的 `why` 回答三件事：**问题是什么**（具体到机制）、**别人会怎么看**（会怎么反应、会追问什么）、**为什么这个改法可行**（尤其当改法有代价时）。

### 六条要求

**一、给证据，带行号。**
> 「同一篇论文对同一工作给了两种互相冲突的描述。Introduction（:164）说 BAN 是『the only method that searches for adversarial neuron perturbations in the parameter space』；而你们自己的 Related Work（:288）写的是 BAN『jointly optimizes a latent feature mask and adversarial neuron noise』——它同时动了特征空间。」

**二、算给他看。** 涉及数字的把重算过程摆出来：
> `0.961375 − 0.888750 = 7.2625 → 应为 7.3`，正文写 7.2

**三、说清后果的量级。**
> 「审稿人拿计算器一按（136.8 ÷ 42.1 = 3.249）就会发现」

比「建议核对」有用得多。

**四、承认代价，别只说好处。** 改法牺牲了什么就直说，让作者自己权衡：
> 「篇幅约 60 词，如果卡页数，可以从 m13 压缩出的空间里出。」

**五、交叉引用其他条目。** 同一问题在多处出现时点明联动：
> 「这条与 k1（贡献点 overclaim）、i9（Introduction 措辞）是同一个问题的三个出口，**三处要一起改**，否则口径不一致反而更糟。」

**六、需要作者拍板的，用 `⚠️` 明说。** 无法离线核实的、依赖作者实验记录的、两种改法都合理的：
> 「⚠️ 这条我无法离线核实。请你自己确认后再改——你比我们都熟这篇。」

### 反面例子

```python
why='表述不够准确，建议改进措辞。'    # 等于没写
why='这里有语法错误。'                 # 没说是什么错、为什么是错
why='审稿人可能不喜欢。'               # 没有具体后果
```

### 修正自己的条目时

审阅过程中会推翻自己先前的判断。**不要悄悄改掉**——在 `why` 里写明：

> **⚠️ 本条已被推翻并重写，方向与我最初的建议相反。**
> 我原本判断……，但核实后发现……

这既是对作者诚实，也让作者知道哪些结论经过了二次验证。

## 页面交互（作者侧）

| 操作 | 效果 |
|---|---|
| 点击标记 | 右侧弹出原文／改后／为什么改 |
| `←` `→` | 按文档顺序逐条浏览（自动滚动定位） |
| `Esc` | 关闭 |
| **标记视图 / 终稿视图** | 前者原文与改写并排；后者隐藏删除内容，读改完的连贯版本 |
| **全部 / 仅必改** | 淡化非必改项 |
| 「标记为已处理」 | 勾选后标记变淡，进度存 `localStorage` |
| ◐ | 明暗主题切换 |

窄屏下右侧批注栏自动变成底部抽屉。

**一章一个文件**——`localStorage` 键由输出文件名推导，分页各自独立记状态。
