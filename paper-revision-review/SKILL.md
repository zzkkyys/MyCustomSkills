# 论文修订审阅页

## 用途

把「一堆修改建议」变成**作者能一眼看懂、能逐条决策、能直接转给别人**的东西。

传统做法（在聊天里列 20 条、或者直接改文件）有两个问题：作者不知道每处改动**动了什么**，也不知道**为什么要改**。这个 skill 产出的是一张稿纸：原文与改写并排显示，点任意一处就看到理由；作者可以只看必改项，可以逐条勾掉，可以切到终稿视图读改完的连贯版本。

**产物是单文件 HTML，零外部依赖，离线可用**——可以丢进 Dropbox、发邮件、拷 U 盘，双击就开。

---

## 快速开始

```bash
SKILL=~/path/to/paper-revision-review          # 本 skill 目录
cp $SKILL/assets/example_review.py ch3_review.py
# 编辑 ch3_review.py：填 TITLE / LOC / INTRO / SECTIONS / CHANGES
python3 $SKILL/scripts/build_review.py ch3_review.py revision-review-ch3.html
open revision-review-ch3.html
```

`build_review.py` 会做五重校验，任何一项不过就报错退出、不写出半成品：

1. `SECTIONS` 里每个 `data-id` 都有 `CHANGES` 条目
2. 每个 `CHANGES` 键都在 `SECTIONS` 里被用到
3. 字段完整、`src`/`sev`/`type` 取值合法
4. 标签成对闭合
5. `<del>`/`<ins>` 必须包在 `.chg` 里（否则是点不开的死标记）

外加：产物零外部引用、有 DOCTYPE 与 charset（否则中文乱码）。

> **一章一个文件。** 不要把全文塞进一页——`localStorage` 键由输出文件名推导，分开建页各自独立记「已处理」状态，互不干扰。

## 四类标记

| 类型 | 写法 | 视觉 |
|---|---|---|
| 修改 | `<span class="chg" data-id="x"><del>旧</del><ins>新</ins></span>` | 红底划线 + 赭底 |
| 新增 | `<span class="chg" data-id="x"><ins>新</ins></span>` | 蓝底 |
| 删除 | `<span class="chg" data-id="x"><del>旧</del></span>` | 红底划线 |
| 结构 | `<span class="chg brk" data-id="x" data-type="结构"><ins>¶ 说明</ins></span>` | 紫底、独占一行 |

配色沿用校对符号传统：**蓝墨水＝新增、红笔＝删除、赭石＝改写、紫＝结构**。

两个细节：

- **同一 `data-id` 可以用在多个 span 上**——一处改动横跨几个位置时（比如同一个词在三处要统一），点任意一个会全部高亮。
- **`<span class="snip">〔节选〕</span>`** 用来标出被省略的上下文。长段落只标改动句、其余用 `〔……〕` 略过，比贴全文可读。

## 三档严重程度

分档的标准是**审稿人/读者会不会当场发现，以及发现后的代价**，不是改起来费不费力。

| 档 | 判据 | 例 |
|---|---|---|
| **必改** | 一眼可见、或可当场核查坐实的硬伤 | 占位符残留、编译进 PDF 的编辑标记、前后矛盾的数字、引用错论文、页数超限、语法错误 |
| **建议** | 影响说服力与评分，但不是错 | 论证缺口、overclaim、缺限定、信息密度不足、结构问题 |
| **润色** | 不影响判断，只影响观感 | 术语统一、冗词、排版细节 |

**必改项应当少而硬。** 如果一章 30 处里 25 处是必改，这个分档就失去了意义——作者赶时间时第一件事就是筛「仅必改」，那份清单必须真的是「不改就完了」的东西。

## `why` 字段是这个 skill 的全部价值

`before`/`after` 只是 diff，任何工具都能给。**作者真正需要的是 `why`。** 一条合格的 `why` 回答三件事：

1. **问题是什么**（具体到机制，不是「不够严谨」）
2. **别人会怎么看**（审稿人/读者会怎么反应、会追问什么）
3. **为什么这个改法可行**（尤其当改法牺牲了什么的时候）

写作要求：

- **给证据，带行号。** 「与 `:288` 自相矛盾」远胜于「表述不一致」。能引原文就引原文。
- **算给他看。** 涉及数字的，把重算过程摆出来（`0.961375 − 0.888750 = 7.2625 → 应为 7.3`）。
- **说清后果的量级。** 「审稿人拿计算器一按就会发现」比「建议核对」有用。
- **承认代价。** 如果改法会损失什么（篇幅、语气强度），直接说，让作者自己权衡。
- **交叉引用其他条目。** 同一问题在多处出现时（`见 k1 / s10 / t4`），要点明「三处必须一起改，否则口径不一致反而更糟」。
- **需要作者拍板的，明说。** 无法离线核实的、依赖作者实验记录的，标 `⚠️` 并说明要确认什么。

反面例子：`why='表述不够准确，建议改进措辞。'` —— 这等于没写。

`why` 支持行内 HTML（`<strong> <em> <br> <table>`），复杂对照用小表格。

## 分章审阅

每一章有各自的高频问题，逐章过比通读一遍找得准。清单见 `references/分章审阅清单.md`，涵盖摘要与引言、相关工作、理论、方法、实验、结论与全文收尾。

两条通用纪律：

**一、跨章节自洽性是问题密度最高的地方。** 单章内部读起来都通顺，矛盾几乎全在章节之间：同一个符号两种定义、同一个基线两种归类、同一个数字两个值、贡献点声称的强度超过定理实际证明的。**审每一章都要把它和其他章对读。**

**二、浮动体位置和全文级完整性要专门查一遍。** 这两类问题通读时会被完全忽略，但代价可能最大——图表声明位置远离首次引用、附录被并进主文导致页数超限、缺局限性/伦理声明。**最后务必实际编译一次数页数。**

## 第二意见

让另一个模型独立复审同一章，再做三方对照，能显著提高覆盖率——实践中约三分之一的问题是单方发现的。

流程与 prompt 模板见 `references/第二意见与核实.md`。核心纪律只有一条：

> **别人报的问题，先核实再采信。**

第二意见会给出**看起来很具体、实际不成立**的断言（引用不存在的 URL、报错的行号、图里根本没有的文字）。同时它也会**推翻你自己的结论**——这种时候要立刻验证并如实更正，在条目里写明「本条已被推翻并重写，方向与我最初的建议相反」。

合并后给每条打来源标记（`both` / `codex` / `mine`），页面上会显示成「双方共识 / Codex 提出 / 本轮提出」。**共识项最可靠，应当优先改。**

## 常见陷阱

| 陷阱 | 后果 | 对策 |
|---|---|---|
| 只标了 span 忘了写条目 | 点不开的死标记 | 校验器会拦；先写 `CHANGES` 再写 `SECTIONS` |
| 全文塞进一页 | 「已处理」状态互相干扰 | 一章一文件 |
| 必改项过多 | 分档失效，赶时间时没法筛 | 严守「一眼可见/可当场坐实」的判据 |
| 用表里已四舍五入的值验算 | 得出「全部一致」的错误结论 | 永远用未舍入的原始值重算 |
| 建议加了一堆内容却没查页限 | 改完超页 | 先编译数页数，定出版面预算，先删后加 |
| 直接采信第二意见的外部引用 | 把错的当对的写进条目 | 能本地核实的必须核实，不能的标 `⚠️` 交作者 |

## 目录

```
paper-revision-review/
├── SKILL.md
├── assets/
│   ├── template.html          # 单文件外壳（CSS + 交互 JS + 占位符）
│   └── example_review.py      # 最小可运行示例，复制改内容即可
├── scripts/
│   └── build_review.py        # 渲染 + 五重校验
└── references/
    ├── 分章审阅清单.md         # 各章高频问题
    ├── 标注约定.md             # 标记/分档/来源/why 的完整规范
    └── 第二意见与核实.md        # 复审 prompt 模板与核实纪律
```

改模板样式直接编辑 `assets/template.html`；它的 CSS 用 token 组织，明暗两套主题都在 `:root` 里，改配色只需动 token。
